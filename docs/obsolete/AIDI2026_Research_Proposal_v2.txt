===== PAGE 3 =====

Problem & Motivation
The Challenge
• Industrial AGVs depend on WiFi for real-time 
control and navigation feedback
• WiFi quality fluctuates unpredictably — metal 
shelving, corridors, moving obstacles
• Signal drops → AGV stops → production 
downtime
• Current monitoring is reactive (detect after 
degradation), not proactive
• Operators cannot understand why signal degrades 
at specific locations
The Opportunity
• AGVs already carry LiDAR for navigation — it sees 
the physical environment
• Environmental geometry (obstacles, corridors, 
open areas) directly affects WiFi propagation
• AGV telemetry (position, heading, speed) provides 
operational context
• XAI can explain why signal degrades —
actionable for operators & network planners
Can we use the AGV's own LiDAR to predict and explain WiFi quality proactively?

===== PAGE 6 =====

What Is Novel?
1
LiDAR geometry → WiFi quality
Using obstacle density, corridor shape, LOS blockage from the AGV's own LiDAR as predictors for WiFi signal quality. No prior
work does this.
2
XAI for WiFi degradation causes
SHAP explanations revealing why signal degrades at specific locations (blocked LOS, cluttered environment, antenna 
misalignment during turns).
3
Multi-hotspot with explainability
Predicting quality per hotspot with per-AP explanations: why is AP-A better than AP-B here? Directly actionable for network 
planning.
4
Real industrial AGV context
Validated on real data from an operational AGV — not simulation, not outdoor vehicles, not static testbeds.

Methodology — Feature Engineering
LiDAR Geometric
Per-sector (K=6–8 sectors):
• mean_dist, var_dist
• obstacle_count
• openness, min_dist
Aggregate scan:
• corridor_index
• symmetry_index
• clutter_score
• scan_entropy
AGV Telemetry
Navigation state:
• position_x, position_y
• heading, speed
• nav_segment, confidence
Dynamic state:
• is_turning, is_stopped
• inclination_x/y
Operational:
• battery, power draw
• load_weight (strain gauge)
Hotspot-Relative
Geometric relation:
• dist_to_hotspot
• angle_to_hotspot
LiDAR-derived:
• los_blockage_ratio ★
• path_obstacle_density
Identity:
• hotspot_id (A / B)
★ los_blockage_ratio = the critical feature linking LiDAR geometry to WiFi prediction

===== PAGE 8 =====

Evaluation — Four Protocols
The heterogeneous run structure enables rigorous generalization testing across routes and hotspot configs
P1: Cross-Route
Predict WiFi on an unseen route (same hotspot config)?
Leave-one-route-out CV within runs sharing the same hotspot 
config
Spatial generalization
P2: Cross-Hotspot
Predict WiFi for an unseen access point?
Train on runs with one set of APs, test on runs with different APs
AP-agnostic physics
P3: Full Leave-One-
Run-Out
Predict on entirely unseen (route, hotspot) combo?
Leave one full run out — both route and hotspot unseen 
together
Deployment readiness
P4: Multi-AP Ranking
Which AP is best here, and why?
In multi-hotspot runs, rank APs and explain via SHAP 
decomposition
Actionable for planners

Risks, Concerns & Countermeasures
WiFi has low variance (signal uniformly good) Use ping as alternative target; focus on regression; frame as quality 
assurance
LiDAR features don't beat distance-only baseline Publishable negative result — "distance dominates in this setting" + 
XAI analysis of the regime
Multi-hotspot runs not available in time Paper viable on single-hotspot runs (P1+P2). Multi-AP ranking (P4) 
becomes future work
LiDAR RSSI unavailable Already accounted for — all features use distance-only. No 
methodology impact
Timestamp sync issues across streams Nearest-neighbor matching + tolerance threshold + rolling-window 
smoothing on WiFi
Concern Countermeasure
